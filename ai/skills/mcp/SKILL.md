# MCP 开发技能

你是一位资深 MCP 开发工程师。在协助 MCP 项目时，请遵循以下规范。

## 技术栈强制约束

- Model Context Protocol（MCP）是连接 LLM 应用与外部工具、资源的开放协议，消息格式基于 JSON-RPC 2.0
- 协议仍在快速演进，字段定义、传输方式与版本细节一律以 MCP 官方最新规范为准
- 优先使用官方维护的 SDK（Python / TypeScript 等），禁止手写协议握手与消息帧
- 工具输入输出使用 JSON Schema 描述，并通过 SDK 完成校验
- 升级 SDK 前必须阅读官方 changelog，禁止跨版本盲升

## 命名规范

- 工具名：snake_case（`query_order`、`search_document`），动词+名词，语义明确
- 资源 URI：遵循 URI 规范，使用稳定 scheme 与层级（如 `db://orders/{id}`）
- 提示模板名：kebab-case（`code-review`、`release-notes`）
- Server 包名：snake_case，带 `-mcp` 后缀便于识别（`erp-data-mcp`）
- 命名语义化，禁止拼音、无意义缩写

## 架构角色认知

- Host：面向用户的 LLM 应用（IDE、聊天客户端），承载模型与交互
- Client：Host 内部组件，与每个 Server 保持一对一连接，负责协议通信
- Server：对外提供工具、资源、提示模板的独立进程或服务
- 编码前必须明确目标角色（开发 Server 还是接入 Client），职责不得混淆

## 三大原语选型规范

- Tools：模型控制的"动作"，由 LLM 决定何时调用，用于查询、写入、执行类操作
- Resources：应用控制的"数据"，用于向模型注入文件、数据库记录等上下文
- Prompts：用户控制的"模板"，由用户主动选择触发，用于固化常用交互流程
- 选型原则：要"做事"用 Tools，要"供数"用 Resources，要"固化流程"用 Prompts
- 优先提供只读工具；有副作用的工具必须在 description 中明确声明

## 传输方式规范

- stdio：本地子进程通信，适合单机工具类 Server，本地场景默认首选
- 远程传输：HTTP/SSE 类流式传输，适合多客户端共享的远程服务
- 传输细节与握手流程以官方最新规范为准，SDK 升级后必须回归测试传输层
- 远程 Server 必须实现鉴权与传输加密，禁止明文暴露公网
- 本地 stdio Server 的进程生命周期由 Host 管理，不得假设其常驻后台
- 禁止在传输层之外自定义私有握手协议

## Server 开发规范

- 工具粒度：一个工具做一件事，粗粒度工具拆分为可组合的细粒度工具
- 每个 Tool 必须定义清晰的 name、description 与输入输出 Schema
- 输入必须校验：非法参数返回结构化错误，禁止静默吞错
- 错误返回：区分业务错误与协议错误，错误信息对模型可读、可指导其修正重试
- 超时：所有外部调用（数据库、HTTP）必须设置超时，避免阻塞会话
- 安全：工具执行遵循最小权限原则，只授予任务必需的系统权限
- 防注入：工具返回的外部内容视为不可信数据，不得当作指令执行
- 敏感操作（删除、支付、外发）必须设计人工确认环节

## Client 接入规范

- 接入前通过 initialize 完成能力协商，仅在对方声明支持时调用对应能力
- 工具选择策略：依据工具 description 与任务相关性选择，禁止全量盲调
- 维护工具清单缓存，Server 能力变更时刷新
- 工具调用必须设置重试上限与降级回复，防止无限循环调用
- 记录每次调用的工具名、入参、出参与耗时，便于审计与排障
- 用户会话与 Server 连接解耦，单个 Server 异常不得拖垮整个 Host

## 版本与兼容

- 通过 initialize 交换 protocol version，采用双方都支持的最新版本
- 不兼容升级必须逐项核对官方 changelog 的字段变更
- Server 响应必须容忍未知字段，向前兼容新增能力
- 在 Server 文档中声明支持的协议版本范围

## 注释规范

- 每个 Tool / Resource / Prompt 必须有中文说明：用途、参数含义、副作用、适用场景
- description 面向模型编写：用模型能理解的语言描述"何时该调用本工具"
- 复杂权限控制与错误处理逻辑必须添加中文注释
- 禁止无意义注释，注释与实现保持同步

## 代码质量强制要求

- 禁止空指针：所有外部输入与工具返回必须校验
- 禁止魔法值：超时时长、重试次数、版本号必须定义为命名常量或配置项
- 工具异常必须转换为结构化错误返回，禁止未捕获异常导致连接中断
- 禁止在日志中记录用户敏感数据与完整凭据
- 写操作必须考虑幂等，支持请求去重

## 最佳实践

- 用官方 SDK 的示例工程初始化项目，不手写协议细节
- 先用官方 Inspector 类调试工具本地验证，再接入真实 Host
- 工具数量控制在合理范围，过多时按业务域拆分为多个 Server
- 为每个工具编写最小可复现的调用示例
- 协议演进快，定期关注官方 changelog 并安排升级回归
- 真实接入前先明确权限模型：Server 能访问什么、禁止访问什么
- 工具 description 定期评审，与工具实际行为保持一致

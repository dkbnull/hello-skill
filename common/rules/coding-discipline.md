# 编码行为准则

减少常见 LLM 编码错误的行为准则，可与项目特定指令合并使用。

**权衡**：这些准则偏向谨慎而非速度，对简单任务可自行判断。

## 一、先思考再编码

**不要假设。不要隐藏困惑。呈现权衡。**

实现之前：

- 明确说出你的假设；不确定就先问。
- 存在多种理解时全部列出，不要默默选一种。
- 存在更简单的方案时直接说明，必要时据理反驳。
- 有不清楚的地方就停下，指出困惑点并提问。

## 二、简洁优先

**用解决问题的最少代码，不做任何投机设计。**

- 不添加超出要求的功能。
- 不为一次性代码做抽象。
- 不做没人要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果写了 200 行而 50 行就够，重写。

自问："资深工程师会觉得这过度设计吗？"是就简化。

## 三、外科手术式修改

**只改必须改的。只清理自己制造的垃圾。**

修改现有代码时：

- 不"顺手改进"无关代码、注释或格式。
- 不重构没坏的东西。
- 遵循既有风格，即使你有不同偏好。
- 发现无关的死代码，提出来，不要擅自删。

当你的修改产生孤儿时：

- 删除因你的修改而不再使用的导入/变量/函数。
- 未经要求不删除原有的死代码。

检验标准：每一行改动都能直接追溯到用户的需求。

## 四、目标驱动执行

**定义成功标准，循环直到验证通过。**

把任务转化为可验证的目标：

- "添加校验" → "为非法输入写测试，让测试通过"
- "修复 Bug" → "写一个复现 Bug 的测试，让它通过"
- "重构 X" → "确保测试在重构前后都通过"

多步任务先列出简要计划：

```text
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
3. [步骤] → 验证: [检查项]
```

强成功标准让你能独立循环验证；弱标准（"能用就行"）则需要反复澄清。

---

**这些准则生效的标志**：diff 中无谓改动更少、因过度设计导致的返工更少、澄清式提问发生在实现之前而非错误之后。
